## Executive summary

The system is well-built for its purpose and unusually well-documented and QC'd for a
personal project. The scraping → classification → static-dashboard architecture is the
right shape: cheap, auditable, and low-maintenance. The pipeline is demonstrably capturing
the real market: your 29 tenure-track ads since March closely match the ~33 TT ads per
secondary cycle (Jan–Jun) that Charles Lassiter reports as the 10-year PhilJobs average.

The biggest opportunities are not code fixes but methodology upgrades:

1. **Backfill historical PhilJobs data instead of waiting three years.** PhilJobs's query
   interface supports *Include expired ads* + posting-date ranges + spreadsheet download,
   and Lassiter has analyzed PhilJobs data back to 2013 this way (~14,200 ads in their DB).
   A one-time backfill + Batch-API classification (~$50–100) would let the dashboard answer
   your primary question — which AOS categories are growing or declining — **now**, against
   a decade of baseline, rather than in 2029.
2. **Fix the stock-vs-flow artifact.** The 2026-03-10 first scrape imported ~100 already-active
   ads as "new jobs that week." Every trend chart therefore shows a phantom collapse after
   March. Until this is fixed, the dashboard's headline visual tells a false story.
3. **Bucket trends by `posted_date`, not `scraped_date`.** You already store PhilJobs's exact
   creation date on every job; using scrape date adds Monday-boundary noise, merges missed
   weeks (the skipped 2026-04-20 run inflated 04-27 to 20 "new" jobs), and caused the
   inconsistency where backfilled weeks 05-18/05-25 use posted-date while all others use
   scrape-date.
4. **Use PhilJobs's own structured category as ground truth for position type.** Every ad
   carries a publisher-supplied `job_category` like "Junior faculty / Tenure-track or
   similar." Deriving position type from that suffix deterministically (with Claude only
   for edge cases) removes a whole class of classification noise.
5. **Decide whether Graduate Fellowships are "the market."** 21 of 245 ads (8.5%) are
   graduate fellowships — postings for current PhD students, not job-market candidates —
   and Claude currently splits them inconsistently (16 → Other, 5 → Postdoc/Fellowship).

## Part 1 — What's working well

- **Architecture.** Static GitHub Pages + weekly Actions + JSON master file is the right
  cost/complexity point. No server, no database, fully reproducible from the repo.
- **Documentation.** The README's methodology sections (dedup, taxonomy versioning,
  fallback behavior, design rationale) are better than most published research tools.
- **QC infrastructure.** This is the standout. Monthly live-count drift check,
  field-coverage audit with `available_since` grace periods, gap detection, freshness
  alarms, failure-auto-Issues, a regression gold set, per-job `_model`/`_classified_at`
  audit stamps, `classification_vN` history on taxonomy bumps, and a semiannual Opus
  cross-check. Most production data teams do less.
- **External validity.** Cross-checked against Lassiter's published PhilJobs numbers
  (10-yr averages: ~184 junior-TT ads in the Jul–Dec primary cycle, ~33 in the Jan–Jun
  secondary cycle; fixed-term ~145/~157): your Mar–Jul TT count of 29 is right in line.
  The scraper is not silently missing a chunk of the market.
- **Honest known-issues list.** The README documents its own gaps (West Coast modal,
  cross-cutting x-axis) — good practice.

## Part 2 — Strategic critique

### 2.1 The three-year wait is optional: backfill is feasible

Your primary goal ("which AOS categories and position types are growing or declining")
cannot be answered from ~4 months of data, and honestly not confidently from 3 years —
year-to-year market noise is large relative to trend. But it doesn't have to be prospective:

- PhilJobs's job query form has **"Include expired ads"**, a **posting-date range filter**,
  and a **"Download spreadsheet"** export (this is how Lassiter builds 2013–2026 analyses;
  he notes PhilJobs "made their data super easy to download").
- PhilJobs reports ~14,200 ads in its database total. Backfilling even 2015→present
  (~8–10k ads) and classifying via the **Message Batches API** (50% discount) at Sonnet
  prices is roughly **$50–100 one-time**. With Haiku 4.5 it would be ~$10–20, and your
  semiannual Opus QC already gives you the tool to measure whether Haiku is good enough
  for the backfill corpus.
- With 10 years of history, every dashboard chart gains a baseline: this-cycle-vs-same-
  cycle-last-year, AOS share trends, TT vs fixed-term drift — the exact questions you
  built this to answer.

**Caveat to verify:** whether the spreadsheet export includes full description text (needed
for your classifier) or only the summary fields, and whether very old ads retain
descriptions. Even summary-only would still support AOS/position/institution/date analysis,
since the export includes AOS, contract type, and posting date.

### 2.2 Stock vs. flow: the March baseline pollutes every chart

Week 2026-03-10 records 100 "new" jobs — but those are all ads *active on PhilJobs that
day*, posted over the preceding weeks/months. Every trend line consequently starts at a
spike and "declines," which a reader will misread as a collapsing market. The monthly
granularity view makes it worse (March towers over everything).

Fix options (in preference order):
1. Rebucket all trends by `posted_date` (§2.3) — the initial-import ads then distribute
   back over their true posting weeks, mostly solving this automatically.
2. Flag week-1 as `baseline: true` and exclude it from trend charts (keep it in totals),
   with a dashboard annotation.
3. At minimum, annotate the March point on-chart ("initial import — not a weekly rate").

### 2.3 Bucket by `posted_date`, not `scraped_date`

PhilJobs gives you the exact creation time; your QC expects ≥95% coverage of it. Scrape-date
bucketing has three artifacts: (a) everything lands on Mondays, so weekly counts are really
"jobs PhilJobs surfaced in the 7 days before each Monday" — fine until a run is missed;
(b) the missed 2026-04-20 run merged two weeks into the 04-27 point (20 jobs);
(c) your own backfill of 05-18/05-25 already used posted_date, so the series now mixes two
bucketing rules. Rebuilding all of `weekly_trends` from `posted_date` (ISO-week buckets)
is a one-function change in `rebuild_weekly_trends` and makes the series internally
consistent and robust to missed runs. Keep `scraped_date` for provenance.

Note: switching also changes what "new jobs this week" means on the stat card — from
"first seen this week" to "posted this week" — which is the number you actually want.

### 2.4 PhilJobs already tells you the position type

Every ad's `job_category` has the form `<role> / <contract type>` with publisher-controlled
vocabularies (role: Senior faculty, Junior faculty, Faculty (open rank), Postdoc or similar,
Visiting fellowship / Professorship, Graduate fellowship, Research assistant,
Administration, Other; contract: Fixed term, Tenure-track or similar, Tenured/continuing/
permanent, Contract type open). Your five position types are nearly a deterministic
function of this pair, e.g.:

| PhilJobs category | → Position type |
|---|---|
| any role / Tenure-track or similar | Tenure-Track |
| any faculty role / Tenured, continuing or permanent | Tenured / Continuing / Permanent |
| Postdoc or similar / * | Postdoc / Fellowship |
| Visiting fellowship / Professorship / Fixed term | Visiting / Adjunct / Lecturer |
| Junior faculty / Fixed term | Visiting / Adjunct / Lecturer |
| Graduate fellowship / * | (exclude, or its own type — see §2.5) |
| Administration, Other (non-academic) / * | Other |

Current cross-tab of Claude's `position_type` against `job_category` shows real
inconsistencies: 5 of 21 Graduate fellowships → "Postdoc / Fellowship" while 16 → "Other";
"Senior faculty / Tenure-track or similar" ads landing in three different buckets; a
"Junior faculty / Fixed term" ad classified Tenure-Track. A deterministic mapping (with a
weekly QC flag for ads where Claude's free-text reading disagrees — those are interesting,
e.g. ads whose text reveals tenure-track despite a Fixed-term tag) is strictly better than
free-text inference. Keep Claude for what PhilJobs can't give you: the AOS taxonomy
normalization and institution type.

### 2.5 Graduate fellowships are not job-market postings

8.5% of the corpus is ads aimed at current/incoming PhD students. For a dashboard whose
purpose is "what will the market look like when I enter it," these are noise in every
chart they touch (notably Postdoc/Fellowship trends and the Other bucket). Either exclude
them from the dashboard corpus (keep in raw data), or make them a sixth position type so
they're at least visible and separable. Same question, softer, for "Research assistant".

### 2.6 Hiring season: use the primary/secondary cycle framing

The Sep–Jan shading doesn't match how the market actually cycles, per Lassiter's decade of
PhilJobs data: the **primary cycle runs July–December** (TT ads ramp in August, peak
Sep–Nov), and the **secondary cycle (January–June) is the *peak* season for fixed-term
jobs** (~157/cycle vs ~145 in primary) — spring is when VAP/adjunct hiring happens. A
binary "hiring season" shade is therefore misleading for non-TT position types, and
August's omission understates the TT ramp. Recommendation: shade Jul–Dec as "primary
cycle," label Jan–Jun "secondary cycle (fixed-term peak)," and — once you have >1 year of
data — make the headline comparison *same-cycle-last-year*, not week-over-week.

### 2.7 Small-n honesty, especially the West Coast

The West Coast Spotlight currently shows 13 jobs over 4 months, split across 5 metros and
6 AOS colors — i.e., mostly cells of n=1. Nothing wrong with collecting it, but the chart
invites over-reading. Suggestions: display `n=` in every chart subtitle; use 4-week rolling
means on weekly lines; and treat metro-level AOS breakdowns as cumulative-only (which the
spotlight already does — good) until counts reach a threshold (e.g., suppress percentage
labels under n=10). The granularity toggle you added is the right instinct; monthly should
probably be the default view while weekly counts remain this sparse.

## Part 3 — Classification quality

Sonnet-vs-Opus agreement (Jul 15 QC, n=244): main_aos exact-set **86.1%**, position_type
**89.3%**, institution_type **95.5%**. That's solid overall, with three weak spots:

1. **"Open" boundary is the top disagreement class** (77% agreement, and it's your
   largest single category at ~61 jobs). The UTEP example in the QC report shows the
   ambiguity precisely: AOS field says Open, but AOC/description lists teaching needs.
   Rule 2 says any preference disqualifies "Open," but doesn't say whether **AOC-only
   teaching needs count as an AOS preference**. Sonnet says no, Opus says yes — both are
   defensible readings of your prompt. Pick one (I'd suggest: AOC-only signals do *not*
   override an explicit "Open" AOS, since AOC is by definition competence, not
   specialization) and add a worked example to the prompt. This one edit probably buys
   more consistency than any model upgrade.
2. **Non-Western & Cross-Cultural (37.5%, n=8) and Value Theory / Aesthetics (50%, n=10)**
   — small denominators, so don't over-react, but both are "second-tag" categories that
   ride along on multi-AOS ads, which is exactly where Rule 1's "genuinely spans" judgment
   is softest. Worth reviewing the specific disagreements in `qc_opus_2026-07-15.json`
   before the fall cycle starts.
3. **Mega-multi-tag ads inflate category counts.** The Peking University ad carries 7 of
   your 8 main categories; the UCL postdoc 3–5 depending on model. Since the Market
   Overview counts each tag, one omnibus ad adds a unit to nearly every line. Options:
   fractional weighting (1/k per tag) as the default for trend lines, a tag cap, or an
   "omnibus" flag for ads with ≥4 main categories (they're usually effectively Open).

Smaller notes:
- Temperature=0 does not strictly guarantee identical API outputs; "near-deterministic" is
  the accurate claim (README/docs say "deterministic — same input always produces same output").
- The prompt labels the description "excerpt" but the full (EEO-stripped) text is sent —
  fine at ~$1/week, just update the label or truncate deliberately.
- **Model lifecycle over a 3-year collection:** claude-sonnet-4-5 will be deprecated before
  2029. Your mitigations (TAXONOMY_VERSION bump → full reclassify, `classification_vN`
  archives, regression gold set, semiannual Opus reference) are exactly right. Budget for
  ~2 forced model migrations over the project's life and re-run the gold set on each.

## Part 5 — Dashboard suggestions (smaller, incremental)

- Annotate or exclude the March baseline point (§2.2) — highest-value single UI fix.
- Add `n=` sample-size badges to chart subtitles and drill-down modals.
- Default the time-series granularity to **Month** until weekly counts grow.
- Once >1 year of data exists (or after backfill): add a year-over-year overlay view
  (this cycle vs last cycle by week-of-cycle) — this is the chart that will actually
  answer "growing or declining."
- Keyword Explorer: solid engineering (lift-ranked co-occurrence, synonym expansion,
  EEO stripping, published methodology docs), but at 144 US jobs most queries return
  0–2 matches ("emotion" → 1 match, no bubbles). Consider (a) noting the corpus size in
  the UI, and (b) after a historical backfill this feature becomes genuinely powerful —
  e.g., tracking "AI" keyword growth like Lassiter's 1%→16% (2013→2025) finding.
- The README roadmap's accessibility items (ARIA roles, ESC-to-close modal) are worth
  doing; they're cheap.
- Link the dashboard footer to the README/methodology docs — you've earned the
  transparency credit.

## Part 6 — Code review (Opus pass)

Performed by Claude Opus over `scraper.py` (excluding the international dashboard),
`qc_check.py`, tests, all five workflows, README, and the generated `docs/index.html`.
Findings below; the top one was independently re-verified against the live data.

### High severity

**H1. `weekly_trends` is corrupted for every week since 2026-06-01 — trends are computed
before classification and only conditionally rebuilt.**
`save_data` builds each week's trend entry from jobs whose `classification` is still
`None` (classification happens afterward in `main()`), and the entry is only corrected if
`rebuild_weekly_trends` happens to run later — which it does only when there are leftover
unclassified jobs or a state gets resolved. Since 2026-06-01 that hasn't happened, so
**every stored trend entry since June has `main_aos_counts: {}` and all jobs counted as
position type "Other"** (verified: 2026-06-01 through 2026-07-13 all affected). The live
dashboard is unaffected (it recomputes from `jobs`), but the canonical longitudinal
record — `weekly_trends`, `trends_weekly.csv`, and the weekly `report_*.md` files — is
wrong for 7 weeks and counting. *Fix:* call `rebuild_weekly_trends` unconditionally at the
end of `main()`, or compute trends after classification. Then rebuild once to repair the
stored series. **This should be fixed before the fall cycle starts.**

**H2. Keyword Explorer trend chart reads all-zero at the default (Month) granularity.**
The per-bucket match counter indexes full dates (`2026-07-13`) into month-labeled buckets
(`2026-07`), so nothing ever matches; since Month is the default view, every keyword search
shows a flat zero trend line on page load. *Fix:* truncate the job date to the active
bucket label before counting.

**H3. No workflow concurrency control; same-minute schedule collision is real.**
The semiannual Opus QC (Jan 15/Jul 15, 14:00 UTC) and the weekly scrape (Mondays 14:00 UTC)
fire at the same minute whenever the 15th is a Monday (~1 in 7 years of occurrences; e.g.
2026-06-15 was a Monday). All four writing workflows push to `main` with no `concurrency:`
group and no pull-before-push, so the loser's push is rejected and its work discarded.
*Fix:* shared `concurrency: {group: repo-writer, cancel-in-progress: false}` in all
writing workflows, plus `git pull --rebase` before push.

### Medium severity

**M1. Scraped job text is embedded into the dashboard `<script>` without escaping `</`.**
A PhilJobs description containing `</script>` would truncate the inline script and break
the page (a latent stored-injection vector from an external source; no current job
triggers it). *Fix:* `.replace('</', '<\\/')` on the embedded JSON, or move payloads to
`<script type="application/json">` + `JSON.parse`.

**M2. Non-atomic writes to `all_jobs.json`.** Every save truncates and rewrites the 1.2 MB
master file in place; a crash mid-write leaves an unparseable file that the workflow then
commits. *Fix:* write temp file + `os.replace()`; optionally keep a `.bak`.

**M3. README documents an automatic hash migration that doesn't exist in the code.** The
data is already fully ID-based (verified 245/245), so this was done out-of-band — but
anyone following the README's fork instructions against pre-migration data would duplicate
every stored job. *Fix:* correct the README (or add the migration shim).

**M4. Sanitizer doesn't prune `detail_aos` keys to the validated `main_aos`.** A dropped
main category's subcategories would still be counted downstream, allowing a subcategory
tally whose parent line reads 0 (no current occurrences; latent). *Fix:* filter
`detail_aos` keys to `valid_main`.

### Low severity / docs

- L1. `TAXONOMY_VERSION` is `2026-05-18-sonnet-v4` in code; README says `2026-05-16`.
- L2. "Feminist Ethics" exists in `DETAIL_AOS` + prompt but is missing from the README's
  Ethics list (which claims 12 subcategories; code has 13).
- L3/L4. Stale README rows for `hash` and `job_type` (same as Part 4 #1–2); 8 legacy
  `job_type` values now *contradict* `classification.position_type`.
- L5. Generated `SYNONYMS.md` says synonyms were built "by Claude Haiku" — hardcoded;
  actual model is `CLAUDE_MODEL` (Sonnet 4.5).
- L6. `resolve_missing_states` can silently flip a US job to international if Claude
  misidentifies the institution — no logging. Worth a QC log line.
- L7. Year-granularity view shades every bucket as "hiring season" (cosmetic).
- L8. Scraper HTML assumptions (first `<h1>`/`<h2>`, "next"-link text, stop-on-no-new-IDs
  pagination) would fail silently on a PhilJobs redesign — partly mitigated by the
  monthly live-count drift alarm.

### Verified fine

Dedup correctness (all 245 hashes = md5(id), no duplicate IDs); granularity aggregation
math (weekly/monthly/yearly arrays stay aligned; solo/joint sums consistent); no
`new Date()` timezone label bug; division-by-zero guards in percent calcs; no
`INTERNATIONAL` leakage into US jobs; position-type labels/colors consistent everywhere;
Opus QC isolation from live labels; chart dataset/label alignment and modal lifecycle.
