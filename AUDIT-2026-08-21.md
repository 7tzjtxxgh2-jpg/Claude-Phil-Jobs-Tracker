# PhilJobs Dashboard — Project Audit (2026-08-21)

Scope: the full US pipeline — methodology, statistical validity, classification, code
correctness, automation, documentation, and the US dashboard. The international dashboard's
own charts were excluded by request; the US/International split *rule* is in scope.

This is a **report-only** audit. No file in `scraper.py`, `data/`, `docs/`, or
`.github/workflows/` was modified. This document is the only addition.

**Method.** Five parallel Sonnet audit agents worked disjoint surfaces (data integrity,
classification, code correctness, ops + docs, dashboard); methodology, statistical power, the
live-market comparison, and synthesis were done directly. Every agent finding was
re-verified against source before entering this report — two were corrected in the process,
and two of my own preliminary claims were corrected by agent findings. Both sets of
corrections are recorded in §10. Every quantitative claim below came from a command actually
run against the repo's real data.

---

## Executive summary

**The engineering is sound. The measurement design is not yet able to answer the question the
project exists to answer.**

The 2026-07-20 overhaul landed almost entirely, and it landed correctly. I recomputed all 23
weeks of `weekly_trends` from `jobs[]` independently and diffed field-by-field: **zero
mismatches**, `baseline_job_count` exact at 95. A separate agent reproduced the same result
bit-for-bit. The aggregation layer, the escaping discipline, the atomic writes, the
concurrency groups, and the deterministic position-type mapping all work as documented.

The problems are three levels up from the code:

1. **Nothing in the current series is interpretable as a trend.** The data covers
   March–August 2026 — one contiguous stretch of the *secondary* hiring cycle, with no
   year-over-year pair. The headline chart's >50% apparent decline is the known seasonal shape
   of that cycle plus Poisson noise, not a market change. The primary cycle (Jul–Dec), where
   most tenure-track hiring happens and where your actual question lives, is essentially
   unobserved.

2. **The three-year plan will not fix this.** 81% of the category-week cells the dashboard
   draws lines through contain 0, 1, or 2 jobs. After the full three years of collection, the
   smallest change detectable in even the largest AOS category is about **1.35×**. A 25%
   shift in Ethics hiring — precisely the magnitude that should move a specialization
   decision — remains invisible, and never becomes visible by waiting longer.

3. **The fix already exists and costs about $30.** PhilJobs exposes a "Download spreadsheet"
   control and an include-expired-ads option; a documented example pulled 6,510 ads back to
   August 2013. Classifying ~8,000 historical ads with the Batch API and prompt caching costs
   **$29**. That single step takes minimum detectable change to ~1.2×, and is the only route
   to separating trend from season. The prior audit identified this as the highest-value
   improvement and filed it under "when convenient." It is the buried lede of this project.

**Why it hasn't happened is structural, and that is the most useful finding here.** 63% of
`scraper.py` is presentation code, and `docs/index.html` inlines the entire corpus as a
1,156 KB JavaScript blob — 92% of the page, at just 275 jobs. Projected to 8,000 ads that is
a ~33 MB page. `reclassify_all_jobs` rewrites the whole 1.7 MB data file every 10 jobs.
**The highest-value change is gated behind a structural one.** That is why it keeps losing.

Beyond that: one confirmed data bug misfiles Washington DC as Washington State (live in your
data, and it lands in your West Coast view); the monthly QC's failure alarm cannot fire in the
one case it exists to catch; the flagship Opus QC artifact is 100% stale; job records are
write-once, so 130 of 275 jobs have deadlines in the past while all 275 remain `status:
active`; and the README describes an entire dashboard feature that does not exist.

## Part 2 — What is genuinely working

Stated plainly so the critique below is read in proportion.

- **The architecture is right.** Static GitHub Pages + Actions + JSON in git is the correct
  cost/complexity point for a personal longitudinal dataset: no server, no database, every
  historical state recoverable from git. I would not change this.
- **Classify-once-and-store** controls cost *and* keeps the historical series internally
  consistent. Correct instinct, correctly implemented.
- **Using PhilJobs's own publisher-supplied `job_category` as ground truth** for position type,
  with the model only for the ambiguous residue, is exactly the right division of labour — and
  measurably fixed the graduate-fellowship problem the prior audit raised (22 ads now typed
  correctly that Claude splits 18/4 the wrong way).
- **The escaping discipline is real.** `js_json` was tested against `</script>` in every case
  variation, `<!--`, `]]>`, and U+2028/U+2029 — all neutralised or inert.
- **The aggregation math is correct and reproducible**, verified twice independently.
- **`_classification_fallback` is a genuinely good design choice** — it leaves `main_aos: []`
  rather than defaulting to `"Open"`, deliberately keeping failures distinct from real
  readings. (The README describes it incorrectly; the *code* is better than its docs.)
- **The Opus QC is a full census (244/244), not a sample** — more rigorous than assumed.
- **No hardcoded secrets anywhere**; all credential use goes through env/Actions secrets.
- **Real cost is ~$0.08–0.19/week**, well under the documented "<$1/week".

## Part 3 — The central finding: the design cannot answer its own question

### 3.1 Every trend line is one partial season

The series covers **March–August 2026 only** — months 3,4,5,6,7,8, one contiguous stretch, no
year-over-year pair. Philosophy hiring runs a well-defined two-cycle year: primary Jul–Dec
(most TT ads), secondary Jan–Jun (peak for fixed-term). Your window is the secondary cycle
winding down, plus two weeks of the primary ramp.

The headline "Total New Jobs" line falls from 13.50/wk (first four weeks) to 6.63/wk after —
a >50% apparent decline that reads as a market collapse. What it is:

1. **Seasonal.** March is the spring peak of the secondary cycle; new postings by month run
   Mar 54, Apr 33, May 24, Jun 30, Jul 30, Aug 9 (partial). This is the known shape of the
   cycle you are sampling, not a change in the market.
2. **The trailing incomplete week is withheld by design**, so the series always ends low.
3. **Poisson noise.** At λ=7.8/wk a **flat** market produces weekly counts from 2 to 14 —
   spanning almost the entire observed range (1–17).

Two explanations I tested and **ruled out**, so they should not be invoked: it is *not*
baseline contamination (0 of 95 baseline jobs land in any trend week — the exclusion works),
and it is *not* uneven scrape cadence (4 scrapes/27 days early vs 19/133 after — one per 6.8
vs 7.0 days, effectively identical).

**No trend currently shown can be separated from seasonality.** That is not a bug — it is the
unavoidable consequence of five months of single-season data, and it is precisely what the
backfill fixes.

### 3.2 Statistical power: 81% of plotted cells hold 0–2 jobs

184 AOS category-week cells (8 categories × 23 weeks): **41.8% zero, 25.0% one, 14.1% two**.
Only 11 of 184 hold ≥5. Position-type cells: 81.2% hold 0–2. Mean is 7.8 new jobs/week — not
the ~12 implied by 275/23, because 95 are baseline.

Minimum detectable rate change (80% power, α=.05, exact conditional binomial test on two
Poisson counts, 6k simulations/point, cross-validated against the variance-stabilising normal
approximation):

| AOS category | /wk | today | after the 3-year wait | with backfill to 2013 |
|---|---|---|---|---|
| Open | 2.57 | 2.0× | 1.35× | 1.15× |
| Science, Logic & Mathematics | 2.00 | 2.25× | 1.35× | 1.2× |
| Ethics | 1.96 | 2.25× | 1.35× | 1.2× |
| Social & Political Philosophy | 1.52 | 2.25× | 1.5× | 1.2× |
| History of Philosophy | 1.17 | 2.5× | 1.5× | 1.25× |
| Metaphysics & Epistemology | 1.09 | 3.0× | 1.5× | 1.25× |
| Value Theory / Aesthetics | 0.17 | 8.0× | 2.5× | 1.6× |
| Non-Western & Cross-Cultural | 0.09 | >10× | 3.5× | 2.0× |

Columns: today = 23 weeks in 11.5-week halves; 3-year wait = 156 weeks in 78-week halves;
backfill = ~13 years in 338-week halves. Rates are taken from the observed Mar–Aug window (the
quieter cycle), so the backfill column is **conservative**.

**Today nothing below a 2.25× swing is detectable in even the largest category. Three more
years of collection tops out at ~1.35×.** Two categories are hopeless at any horizon without
more history: Value Theory/Aesthetics has **4 jobs total** across 23 weeks; Non-Western has **2**.

### 3.3 The backfill: available now, ~$29, and the only thing that fixes 3.1 and 3.2

PhilJobs has a **"Download spreadsheet"** control on search results and an option to include
expired ads. A documented November-2023 example retrieved **6,510 ads back to August 2013** in
a single download — done independently by Frank Saunders Jr., so this is a demonstrated path,
not a theory. By 2026 that is ≈8,000 ads.

Measured cost using real token counts from your own corpus (1,950-token static prompt +
~1,012 tokens/job + ~250 out):

| approach | 8,000 ads |
|---|---|
| as currently built (Sonnet, no cache, no batch) | $101 |
| + prompt caching | $59 |
| **+ Batch API** | **$29** |
| Opus 5 instead, batch + cache | $49 |
| Haiku 4.5, batch + cache | $10 |

Ongoing weekly cost also falls, from $6.57/yr to $1.92/yr. **Cost was never the blocker.**

This single step converts the project from "answers in 2029" to "answers this month," gives
you ~13 seasonal cycles so trend can finally be separated from season, and takes the West
Coast question from 13 observations to a usable sample.

### 3.4 Why it hasn't happened — the structural gate

- `docs/index.html` is 1,253 KB, of which a single inline `const data = {...}` is **1,156 KB
  (92% of the page)** — the whole corpus ships to the browser on every visit. At 8,000 ads
  that is ~33 MB.
- `all_jobs.json` is 6,260 bytes/job (~48 MB at 8,000), and `reclassify_all_jobs` checkpoints
  by rewriting the **entire file every 10 jobs** — 800 full rewrites, quadratic in corpus size.
- 63% of `scraper.py` is presentation (`generate_trend_dashboard` 2,114 lines +
  `generate_intl_dashboard` 1,663 + `_write_methodology_doc` 322 = 4,099/6,558), and **68% of
  the US dashboard's substantial lines are byte-identical in the international one** — a chart
  fix in one does not fix the other.
- There is **no inference layer at all**: no seasonal adjustment, no confidence intervals, no
  significance testing, no "insufficient data" state. Raw counts go straight to Chart.js.

"Just run the backfill" does not work against this design. That is the real reason §2.1 has
sat undone.

## Part 4 — Correctness findings

*Finding IDs are stable identifiers used by the action list in Part 10; they are not a ranking.
Within each Part, findings are ordered by severity.*

### F-1 [CRITICAL] Washington DC is silently misfiled as Washington State
`extract_location_data` (`scraper.py:526`) iterates `US_STATES` in **dict order** and returns
on the first `\b<name>\b` match **anywhere** in the location string, rather than parsing the
state field. `'Washington': 'WA'` (:33) precedes the four DC entries (:35), so those DC entries
are **dead code** — DC count across the entire dataset history is **0**.

Confirmed live: the Aspen Institute posting at `"Washington, District of Columbia, United
States"` is stored `state='WA'`. Washington State's *only* job is not in Washington State.

7 of 16 realistic location strings mis-parse:

| location | expected | got |
|---|---|---|
| `Washington, District of Columbia, US` | DC | **WA** |
| `Charleston, West Virginia, US` | WV | **VA** |
| `Kansas City, Missouri, US` | MO | **KS** |
| `Indiana, Pennsylvania, US` | PA | **IN** |
| `Delaware, Ohio, US` | OH | **DE** |
| `Georgia, Tbilisi` (the country) | None | **GA** |

Every West Virginia job becomes `VA`; "Georgia" the country becomes a US state, pulling an
international ad into the US dashboard. Impact lands squarely in your priority area: the DC ad
appears in the **West Coast Spotlight**, and DC is documented as Northeast but counted as West.
At 275 ads this is 2 errors; at 8,000 backfilled ads it is systematic.
**Fix:** parse the state from the comma-delimited *field*, match longest-name-first, DC before WA.

### F-2 [HIGH] The monthly QC's failure alarm cannot fire in the case it exists to catch
`.github/workflows/monthly-qc.yml:40-70`. The step is:
```yaml
run: |
  python qc_check.py 2>&1 | tee qc_output.txt
  echo "exit_code=${PIPESTATUS[0]}" >> $GITHUB_OUTPUT
```
Actions' default shell is `bash --noprofile --norc -eo pipefail`. When `qc_check.py` exits 1 —
which it does *only* when it finds ERROR-level problems (`qc_check.py:319-320`) — `pipefail`
propagates the failure and `-e` aborts the step **before the `echo` runs**. The subsequent
"Commit QC report" and "Post QC report as GitHub Issue" steps lack `if: always()`, so Actions
skips both. Reproduced locally under the exact shell flags: the `echo` line never executes.

**The QC report is neither committed nor posted precisely when it finds something.** The
author's own comment ("so GitHub Actions marks step as failed") shows the intent; the bug is in
the interaction. **Fix:** `set +e` around the python call, or `if: always()` on both later steps.

### F-3 [HIGH] Job records are write-once — `status` never updates
`save_data` (`scraper.py:878`) merges only genuinely-new hashes, so every field freezes at
first scrape. Verified: **all 275 jobs are `status: 'active'`**, none has ever become
`expired` in five months — while **130 of 275 have deadlines already in the past**. The
`status` field is effectively meaningless, and `deadline`/`title` corrections made upstream are
never picked up.

### F-4 [MEDIUM] `_parse_pj_date` cannot read PhilJobs's relative dates — latent, not yet fired
`_parse_pj_date` (`scraper.py:1323`) does not match PhilJobs's **relative date strings**. All
**22 of 275** jobs with an unparseable `posted_date` (plus 2 `deadline`s — 8% overall) are
`"Today, 2:04pm UTC"` or `"Yesterday, 3:10pm UTC"`. `job_week_bucket` (:389) silently falls back
to `scraped_date` for these.

**Corrected during this audit — my initial reading was wrong.** I first reported this as an
active leak re-contaminating the early trend weeks. Verified false:
- "Today"/"Yesterday" means the ad was posted 0–1 days before that scrape, so these are
  **genuinely new ads**, not pre-tracking baseline. Bucketing them by `scraped_date` is
  therefore almost always *correct*.
- **0 of 95** identified baseline jobs land in any trend week — the stock-vs-flow exclusion
  works cleanly, exactly as designed.
- **0** of the 22 are currently misbucketed: none is a `"Yesterday"` scraped on a Monday.

The bug is real but **dormant**. Because the cron runs Mondays, the first `"Yesterday"`
(i.e. Sunday) posting it encounters will be bucketed a full week late, permanently.
**Fix:** resolve relative dates against `scraped_date` at parse time.

### F-5 [HIGH] A broken listing fetch silently degrades to a homepage subset
`get_job_ids_from_listing` (`scraper.py:556`) wraps the whole paginated fetch in
`except Exception` and falls back to scraping the homepage, returning those IDs through the
normal success path with only a `print`. A markup change or transient failure yields a small
subset reported as a complete scrape. Related: the function returns `[]` without raising if
the selector breaks entirely, producing a "successful" empty scrape.

### F-6 [MEDIUM-HIGH] `Grad Fellowship / RA` is unreachable by the model, and 2 call sites read the raw field
`CLASSIFICATION_PROMPT` (:473) tells the model to pick "exactly one of the **five** values
below" — `Grad Fellowship / RA` never appears in the prompt. All 22 deterministic
grad-fellowships therefore carry a wrong *raw* `classification.position_type` (18 → `Other`,
4 → `Postdoc / Fellowship`), which accounts for ~63% of all position-type disagreement measured
in the semi-annual QC.

`effective_position_type` masks this at 10 call sites, but **2 read the raw field**:
`generate_report` (:6386), so the committed weekly markdown in `data/report_*.md` carries wrong
labels (a "PhD position" rendered `Postdoc / Fellowship`), and `_compute_cooc_from_jobs` (:1261),
where `is_faculty = position_type != 'Other'`. Dashboard and CSV are right; the weekly reports
are wrong; they disagree with each other.
**Fix:** add the sixth value to the prompt enum; route both raw call sites through
`effective_position_type`.

### F-7 [MEDIUM] Systemic classification failure is invisible to automation
A bad API key, an SDK breaking change, or a retired model is caught by the broad
`except Exception` in `classify_job_with_claude` (:927-1002) and degrades silently to fallback
classifications. `qc_check.py` never checks the `classification_failed` rate, so nothing alarms.

### F-8 [MEDIUM] `semiannual-opus-qc.yml` has no failure notifier at all
Unlike `weekly-scrape.yml`, which correctly opens an Issue on failure. A failure here could go
unnoticed for six months.

### F-9 [MEDIUM] Sanitizer coercion is unmarked and contradicts the fallback's own design
`_classification_fallback` (:912) deliberately avoids `"Open"` — its docstring says so
explicitly. But the sanitizer 50 lines later (:966-968) handles the same underlying failure the
opposite way: `if not valid_main: valid_main = ['Open']`, with **no marker written**. A response
that parses but names only non-canonical categories becomes indistinguishable from a genuine
Open posting.
**Not currently material** — checked all 81 stored `Open` jobs, and 79 are genuinely open on the
evidence of their AOS text or reasoning; 0 jobs carry `classification_failed`. Reported as an
auditability gap, not a data-quality claim.

### F-10 [MEDIUM] No dependency pinning anywhere
All five workflows run `pip install requests beautifulsoup4 anthropic` unpinned; there is no
`requirements.txt` or lockfile. The `anthropic` SDK has a 0.x→1.x major version. Pipeline
behaviour can change with no commit to the repo.

### F-11 [MEDIUM] Atomic-write guarantee is inconsistently applied
`write_json_atomic` (:349) protects `all_jobs.json`, but `docs/index.html`,
`docs/international.html`, the markdown docs and the CSVs are written directly. No `fsync`
before `os.replace` (low impact under Actions).

### F-12 [LOW–MEDIUM] Weekly cron drifts an hour for ~4 months/year
`0 14 * * 1` is 9:00 AM Central during CDT but 8:00 AM during CST. The README's claim is
accurate as scoped but incomplete. Also unaddressed: GitHub disables scheduled workflows after
60 days of repo inactivity, and there is no watchdog for the pipeline going dark.

### F-13 [LOW] CDN `<script>` tags without Subresource Integrity
Tailwind, Chart.js, D3 and TopoJSON load from CDNs with no SRI hashes, several unpinned to an
exact version.

### F-26 [MEDIUM] The synonym-map disk cache can never hit
`generate_synonym_map` (:1494) keys its cache on `md5(model + '\n'.join(vocab[:150]))` — md5 is
deterministic, but its **input** is not. `vocab` is built at :1463 with
`sorted(..., key=lambda t: -term_doc_freq[t])` — **no tie-breaker**. Python's sort is stable, so
terms with equal document frequency keep the iteration order of the underlying set, which *is*
affected by hash randomisation. Verified: three separate processes on byte-identical data
produced three different `vocab_hash` values (`b551…`, `85dc…`, `536e…`) with `n_vocab` fixed at
2717. The `if meta['vocab_hash'] == vocab_hash` check at :1507 therefore always fails and the
"skip the API" fast path never fires.
**Fix (one line):** `key=lambda t: (-term_doc_freq[t], t)`.

### F-27 [MEDIUM] `weekly_snapshots` new-job accounting disagrees with `jobs[]`
2 of 25 snapshot dates disagree with the jobs actually first seen on that date: **2026-03-21
records 0 new jobs while 18 jobs carry that `scraped_date`**, and 2026-03-16 is off by one.
No effect on `weekly_trends` (verified — the recompute is exact), but it contradicts the
README's claim that snapshots are "useful for auditing," which is the one job they have.

## Part 5 — Classification and QC

### F-14 [CRITICAL] The Opus QC artifact is 100% stale, and nothing detects it
`data/qc_opus_2026-07-15.json` compared `claude-opus-4-5` against `claude-sonnet-4-5` across a
**full census of 244 jobs**. Verified: **all 244** of those jobs carry a current
`_classified_at` of **2026-07-20** — the taxonomy-v5 migration overwrote every Sonnet-side
classification the QC had judged, five days after it ran.

`docs/QC_REPORT.md` therefore reports agreement against classifications that no longer exist in
the dataset. Neither `run_opus_qc` (:1613) nor `_write_qc_report` (:1720) references
`TAXONOMY_VERSION`, so nothing flags it. Separately, Opus and Sonnet are given the **identical**
prompt, which makes the QC structurally blind to shared-prompt gaps — exactly like F-6.
**Fix:** stamp each QC run with the taxonomy version it evaluated and invalidate on bump; vary
the prompt (or the reasoning path) between the reference and QC models.

### F-15 [HIGH] No per-job `_taxonomy_version` stamp
Every job carries `_model` and `_classified_at` but no taxonomy stamp, so
`migrate_to_current_taxonomy` (:820) cannot tell from a record whether it is stale. Provenance
has already been permanently lost three times — `classification_history.json` holds
`classification_v1/v2/v3` placeholders — across six taxonomy versions in five months.

### F-16 [HIGH] Rule 1a (applied ethics stays under Ethics) is violated in 29% of eligible cases
The prompt states the rule absolutely and gives the exact forbidden example:
> "AI Ethics" → `["Ethics"]` … — **NOT also Science, Logic, & Mathematics**

Measured across all 275 jobs — of the **51** jobs carrying an applied-ethics subcategory
(AI/Tech Ethics, Bioethics, Environmental, Business, Neuro, Animal, Food):

| | n |
|---|---|
| Rule 1a respected (Ethics only) | 36 |
| **Rule 1a violated (multi-category)** | **15 (29%)** |

Co-tagged category in those violations: **Science, Logic & Mathematics 11**, M&E 4,
Social & Political 3, History 2. Job 30461 is verbatim the prompt's own forbidden example:
`main_aos: ['Ethics', 'Science, Logic, & Mathematics']` with
`detail_aos: {Ethics: ["AI, Technology, and Information Ethics"], Science…: ["Philosophy of
Computing / Philosophy of AI"]}`.

This sits on the highest-volume ambiguous boundary in the taxonomy and a fast-growing one
(AI-related PhilJobs ads went from ~1% in 2013 to 16% in 2025).

**Worth reconsidering rather than just enforcing:** job 30461's description asks for
"philosophy **or** ethics of AI" — genuinely both. The rule may be too absolute for dual
postings. Either add an explicit exception for ads that request both, or enforce it strictly
— but the current state, where the rule is absolute and ignored 29% of the time, gives you the
worst of both: unpredictable double-counting that inflates F-21 and F-22.

### F-17 [LOW] The EEO stripper also feeds the classification prompt, undocumented
`_strip_eeo_boilerplate` (:1376) is called at **:948 (the classification prompt)** and
**:1660 (the Opus QC input)**, not only at :1416 (the keyword index). Its docstring justifies
only the keyword-search use — "flood the keyword search with terms" — and accepts a trade-off
("some real content may be lost") that was reasoned for keyword search and is silently applied
to classification.

**Downgraded after testing.** An agent reported this as demonstrably deleting AOS signal for
identity-related subcategories. Checked against all 275 real descriptions: **zero** stripped
sentences contain a substantive AOS phrase (`philosophy of race/gender/disability`, `feminist
philosophy`, `queer theory`, `disability studies`, …). On a constructed adversarial case the
2-trigger threshold behaved *correctly*, keeping "The Department seeks a specialist in the
philosophy of disability." and stripping only the EEO sentence. The heuristic is better chosen
than it looks. Residual risk is narrow — a sentence needs 2+ trigger words *and* substantive
AOS content — so this is a documentation/scope-creep issue, not a live data-quality problem.
**Fix:** document the classification use in the docstring, or gate the stripper to the keyword
path only.

### F-18 [MEDIUM] `institution_type` has no output validation
Unlike `main_aos`, `position_type` and `state_us`, it is written through unvalidated. Currently
collapses to 3 coarse buckets with 77% in one (`Research University` 211, `Teaching College` 48,
`Other` 16) — too coarse to distinguish R1/R2/SLAC/community college, which is the distinction
that matters most for a job seeker.

### F-19 [MEDIUM] Regression gold set is thin and unevenly covered
9 cases for a 6 position-type × 8 category × ~60 subcategory taxonomy. History of Philosophy —
15.3% of the corpus — is entirely untested. The suite also requires a live API key, so none of
the pure deterministic helpers where this audit found bugs (`extract_location_data`,
`_parse_pj_date`, `job_week_bucket`, `js_json`) has any test at all. F-1, F-4 and the Georgia
case are each a handful of assert lines from having been caught pre-commit.

## Part 6 — Methodology findings

### F-20 [HIGH] "Open" is 29.5% of the corpus and carries no specialization signal
81/275 jobs are `main_aos == ["Open"]`; in the trend series 59/180 category-assignments are
Open — the largest single line on the chart. Effective sample for specialization trends is
~121 jobs over 23 weeks (~5.3/wk across 7 real categories). The dashboard's most prominent
trend line is "postings that specify no area."

### F-21 [MEDIUM] Co-occurrence heatmap uses raw counts, which rank by category size
| pair | raw | Jaccard | lift |
|---|---|---|---|
| M&E + Science/Logic/Math | 21 | 0.241 | **2.20** |
| Ethics + Social & Political | 16 | 0.140 | 1.08 |
| Ethics + Science/Logic/Math | 15 | 0.112 | **0.74** |

Ethics+Science is the third-strongest cell by raw count but co-occurs **less than chance**. The
heatmap actively misleads. **Fix:** display lift or Jaccard; keep raw counts in the tooltip.

## Part 9 — Fresh eyes: what a rebuild would change

You asked whether a stronger model would have built this differently. Honest answer: **the
architecture is right and I would keep it.** What I would change is the *order of investment*.

Keep: static site + Actions + JSON in git; classify-once-and-store; taxonomy versioning with
archive-on-bump; publisher-supplied category as ground truth; the QC instinct.

Change:

| Layer | Today | Rebuild |
|---|---|---|
| **Corpus** | 275 ads, forward-only from Mar 2026 | ~8,000 ads back to Aug 2013 via CSV export, then weekly increments |
| **Data** | one 1.7 MB JSON rewritten whole every 10 jobs | SQLite or Parquet; append-only; jobs and classifications as separate tables keyed by taxonomy version |
| **Classification** | sequential, uncached, hand-sanitized JSON | Batch API + prompt caching + schema-enforced structured outputs |
| **Inference** | *does not exist* | seasonal decomposition by cycle; Poisson/negative-binomial regression with year × cycle × category terms; CIs on every point; explicit "insufficient data" states |
| **Presentation** | 2 × ~2,000-line generators, 68% duplicated, corpus inlined | one template + a US/Intl filter; data fetched as a separate JSON |

**The audience is one person.** Modals, drill-downs, choropleths and co-occurrence heatmaps are
a great deal of surface area for n=1 — and that surface area is what has been crowding out the
analysis. The analysis is the product; the dashboard is packaging.

### Moving to a current model: three things break
A naive model-string swap fails in three separate ways.

1. **`temperature=0` is rejected with a 400** on Opus 5, Sonnet 5, Opus 4.7/4.8 and Fable 5 —
   the parameter was removed. Used at **4 sites** (:956, :1088, :1575, :1670). This is more than
   a syntax fix: the README's determinism guarantee *rests on* `temperature=0`. The current
   lever is `output_config: {effort: ...}`, which is not the same guarantee — so the
   methodological claim needs rewriting, not just the code.
2. **`response.content[0].text` assumes the first block is text** — used at **4 sites** (:959,
   :1091, :1578, :1673). Thinking is on by default on Opus 5, so `content[0]` is typically a
   *thinking* block and this raises `AttributeError`. Iterate and select `block.type == "text"`.
3. **Nothing is pinned** (F-10), so the SDK can change under you regardless.

Not used today, all directly applicable: **structured outputs** (would replace ~30 lines of
hand-rolled sanitization with an API-enforced schema, and eliminate F-9 entirely),
**prompt caching** (the 1,950-token static prompt is re-sent uncached on every job), and the
**Batch API** (50% off, and the right shape for the backfill — today classification is
sequential with `time.sleep(0.5)` per job, which alone is 67 minutes of sleeping for 8,000 ads).
